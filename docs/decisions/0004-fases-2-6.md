# ADR 0004 — Etapas 2–6: tickets, mensajes, documentos y operación

- Fecha: 2026-11-08
- Estado: aceptado
- Alcance: `/root/agentbank-go`

## Contexto

Después de Fase 1, el operador pidió implementar hasta la etapa 6 del plan:
tickets/cola, fases/épicas, mensajes, documentos/búsqueda y operación. El
objetivo es paridad funcional con el backend original, manteniendo SQLite y el
binario único.

## Decisiones

### Tickets y cola

- `tickets.number` es correlativo por proyecto; `ref = PREFIX-N`. Se acepta UUID,
  `PREFIX-N` o `key` para resolver tickets.
- `effective_status` se deriva: `abierto` + dependencias hechas/canceladas + sin
  mensajes pendientes = `listo`; si no, `esperando_dependencias` o
  `esperando_respuesta`.
- Los claims usan `BEGIN IMMEDIATE`, lease de 30 minutos y un índice único
  parcial para impedir dos claims activos.
- `ticket_siguiente` ordena fase → épica → ticket → prioridad → antigüedad y
  devuelve `motivo`, `motivos`, `claims_activos` y un `contexto` acotado.
- `ticket_avanzar` implementa cierre, nota y pregunta. El modo `divido` se
  comporta como `sigo` en esta etapa: no crea ticket hijo.

### Fases y épicas

- Un ticket con épica no acepta `phase_id`; la fase efectiva sale de la épica.
- Cerrar fase/épica con pendientes se permite y el evento registra la lista.
- `briefing` no muta ni audita y se recorta a 4 KB.
- `tablero` devuelve fases → épicas → tickets en una lectura.

### Mensajes

- Destinos participante/rol/proyecto, opciones, default y `assume_default_at`.
- `afecta` solo aplica a solicitudes y saca el ticket de `listo` hasta resolver.
- El barrido de defaults es idempotente.
- Convertir un mensaje crea una decisión o un ticket.
- Si una respuesta difiere de un default ya asumido, se crea un ticket
  `Corregir: …` asignado al emisor.
- Handoff se representa con los alias aceptar/rechazar; no tiene un estado
  estructurado separado.

### Documentos y búsqueda

- Versiones inmutables con hash SHA-256; el sync no crea versión si el hash no
  cambió.
- Docs globales: lectura para todos, escritura solo admin de instancia.
- Decisiones/ADRs y glosario usan las mismas tablas de documentos/decisiones.
- Búsqueda con `LIKE` sobre tickets, documentos y mensajes; si el volumen
  crece, se evalúa FTS5.

### Operación

- Import JSON todo-o-nada, máximo 500 tickets, `dry_run` por rollback, modos
  `omitir`/`actualizar` y detección de ciclos.
- Outbox persistente con backoff y dead-letter a los 10 intentos. Webhooks con
  HMAC opcional.
- Long-poll `/v1/novedades` con `wait` máximo 30 s.
- Idempotencia por `(participant_id, Idempotency-Key)` con hash del body, método
  y request URI.
- Rate limit en memoria de 600 requests/minuto por participante.
- Escaneo de secretos en tickets, comentarios, mensajes, documentos, decisiones
  e import.
- Catálogo central de acciones de auditoría; una acción desconocida falla antes
  de escribir.
- Los eventos guardan `session_id`, `origin`, `correlation_id` y
  `parent_event_id`. No se incluyen en el hash para no romper cadenas de Fase 1.

## Consecuencias

- El backend cubre el ciclo de trabajo completo con SQLite.
- Las limitaciones (`divido`, handoff, menciones `@rol`, búsqueda `LIKE`) son
  explícitas y no silenciosas.
- La UI, CLI, MCP, Telegram y contratos quedan para etapas posteriores.
- El hash de auditoría sigue siendo compatible con eventos de Fase 1.

## Dudas abiertas

- ¿`divido` debe crear un ticket hijo en la próxima etapa?
- ¿Las menciones `@rol` deben generar mensajes `info` automáticamente?
- ¿La búsqueda migra a FTS5 cuando supere cierto volumen?
- ¿Los webhooks deben firmar también el timestamp para evitar replay?
